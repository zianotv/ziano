Questão 1 · Kubernetes — atualização e rollback
Após atualizar a imagem de um Deployment para a versão 2.1, surgiram erros. Para voltar à versão 2.0, a equipe apagou todos os Pods, mas os Pods recriados continuaram usando a versão 2.1.
Por que isso aconteceu e qual é o procedimento correto?
● O estado desejado do Deployment ainda declara a imagem 2.1; o retorno deve ser feito com kubectl rollout undo no Deployment
○ O ReplicaSet guarda os Pods apagados e os restaura com a imagem mais recente; é preciso apagar o Namespace
○ Apagar os Pods só funciona com Services ClusterIP; é preciso trocar o tipo do Service
○ O kubelet baixa sempre a imagem mais nova do registry; basta reiniciar o nó
Por quê: O ReplicaSet recria os Pods conforme o template atual do Deployment, que continua com a imagem 2.1. O rollback se faz no Deployment, com kubectl rollout undo (opcionalmente --to-revision), usando o histórico de revisões.
Questão 2 · Alta disponibilidade
Em um Auto Scaling Group atrás de um ALB, uma instância passou a responder erro 500 em todas as requisições. O ALB a marcou como unhealthy e deixou de enviar tráfego a ela, mas o Auto Scaling não a substituiu, e a capacidade efetiva ficou reduzida.
Qual ajuste faz o Auto Scaling substituir instâncias nessa situação?
● Habilitar no Auto Scaling Group os health checks do ELB, além das verificações de status do EC2
○ Aumentar o máximo do Auto Scaling Group, que substitui instâncias quando atinge o limite
○ Desabilitar os health checks do ALB para que o tráfego continue chegando à instância
○ Trocar a AMI do Launch Template, pois o ASG só substitui instâncias criadas com a AMI mais recente
Por quê: Por padrão o ASG considera apenas as verificações de status do EC2 (falha da máquina). Com o health check do ELB habilitado, instâncias que falham no health check do balanceador também são substituídas.
Questão 3 · Kubernetes — probes
Ao listar os Pods, a equipe vê um Pod com STATUS Running, READY 0/1 e zero reinicializações. Ele não recebe requisições do Service, enquanto os demais Pods atendem normalmente.
Qual interpretação é coerente com esse estado?
● A readiness probe está falhando: o Pod foi retirado dos endpoints do Service, mas o container não é reiniciado por isso
○ A liveness probe está falhando, pois esse tipo de falha retira o Pod do tráfego sem reiniciá-lo
○ O Scheduler ainda não escolheu um nó para o Pod, por isso ele não recebe tráfego
○ A startup probe foi concluída com sucesso, o que sempre impede o Pod de receber tráfego
Por quê: Falha de readiness tira o Pod dos endpoints do Service (ele deixa de receber tráfego) sem reiniciar o container. Falha de liveness provocaria reinícios, e um Pod sem nó estaria Pending, não Running.
Questão 4 · Serverless
Após migrar uma API para AWS Lambda, um gestor afirma que a equipe não tem mais nenhuma responsabilidade de segurança, porque não existem servidores para administrar.
Qual divisão de responsabilidades está correta nesse cenário?
● O provedor cuida da infraestrutura e dos patches do ambiente de execução; a equipe continua responsável pelo código, pelas permissões da execution role, pelos segredos e pelo monitoramento
○ O provedor passa a ser responsável também pelas permissões IAM e pela lógica do código da função
○ A equipe passa a aplicar os patches do sistema operacional dos servidores que executam a função
○ Nenhuma das partes precisa monitorar erros, pois o Lambda corrige falhas de código automaticamente
Por quê: No modelo de responsabilidade compartilhada, o provedor administra a infraestrutura de execução; código, configuração, identidade e permissões, proteção de dados e acompanhamento de erros e consumo continuam com a equipe.
Questão 5 · Armazenamento de objetos
Uma aplicação quer que o navegador do usuário envie um arquivo grande diretamente para um bucket S3 privado, sem passar pelo servidor da aplicação e sem entregar credenciais AWS ao usuário.
Qual mecanismo atende a esse requisito?
● Após autorizar o usuário, a aplicação gera uma presigned URL de envio, com prazo de validade curto, para aquele objeto
○ Tornar o bucket público para escrita, removendo o bloqueio de acesso público
○ Distribuir a access key de um usuário IAM com permissão total no S3
○ Montar o bucket como volume EBS no navegador do usuário
Por quê: URLs assinadas também servem para upload: concedem, por tempo limitado, a operação autorizada sobre um objeto específico, com as permissões de quem assinou. O bucket continua privado e o usuário não recebe credenciais.
Questão 6 · Kubernetes — armazenamento
Uma aplicação de fotos executada em um Deployment grava os arquivos enviados em uma pasta do próprio container. Depois de cada atualização da imagem, as fotos antigas desaparecem.
Qual solução, dentro do Kubernetes, preserva esses arquivos entre substituições de Pods?
● Criar um PersistentVolumeClaim, vinculado a um PersistentVolume, e montá-lo no Pod como volume
○ Aumentar o número de réplicas, para que alguma réplica antiga continue guardando as fotos
○ Colocar a aplicação em outro Namespace, que mantém os arquivos dos containers
○ Converter o Service para NodePort, que copia os arquivos para todos os nós
Por quê: O sistema de arquivos do container é efêmero. O PVC solicita armazenamento persistente, que é atendido por um PV (provisionado manualmente ou de forma dinâmica por uma StorageClass), e o Pod monta o PVC. Outra alternativa fora do cluster é usar armazenamento de objetos.
Questão 7 · Redes — Security Groups
As instâncias da aplicação são criadas e removidas pelo Auto Scaling e mudam de IP com frequência. O banco PostgreSQL deve aceitar conexões apenas dessas instâncias.
Qual regra de entrada no Security Group do banco é a mais adequada?
● Permitir a porta 5432 tendo como origem o Security Group das instâncias da aplicação
○ Permitir a porta 5432 de 0.0.0.0/0, pois o banco está em subnet privada
○ Permitir todas as portas a partir da subnet pública, onde fica o balanceador
○ Cadastrar manualmente o IP de cada instância sempre que o Auto Scaling criar uma nova
Por quê: Um Security Group pode usar outro Security Group como origem. Assim, qualquer instância associada ao SG da aplicação é autorizada, independentemente do IP, e nada mais. Abrir para 0.0.0.0/0 ou para todas as portas amplia a superfície de ataque.
Questão 8 · Banco relacional — recuperação
Às 14h10, um comando executado sem filtro apagou os registros de matrícula de um semestre inteiro em um banco RDS com Multi-AZ e uma réplica de leitura. O erro foi percebido às 15h. Os backups automáticos estão habilitados, com retenção de 7 dias.
Qual é o caminho adequado para recuperar os dados?
● Restaurar o banco para um momento logo antes das 14h10 com point-in-time recovery, que cria uma nova instância
○ Fazer failover para o standby da Multi-AZ, que mantém os dados anteriores à exclusão
○ Promover a réplica de leitura, que não recebe operações de exclusão
○ Aguardar a próxima janela de backup, que desfaz automaticamente as exclusões do dia
Por quê: Replicação, síncrona ou assíncrona, propaga a exclusão para o standby e para a réplica. Só os backups permitem voltar no tempo: o PITR restaura para qualquer instante dentro do período de retenção, criando uma nova instância.
Questão 9 · Kubernetes — arquitetura
Durante uma auditoria do cluster, o administrador precisa identificar onde ficam registrados os Deployments, Services, Secrets e demais objetos declarados, além do estado registrado de cada um.
Qual componente do control plane armazena esse estado do cluster?
● O etcd, banco chave-valor consistente que guarda o estado de todos os objetos do cluster
○ O kubelet, que mantém em cada nó uma cópia completa de todos os objetos do cluster
○ O kube-proxy, que grava os objetos declarados nas regras de rede dos nós
○ O Scheduler, que guarda o histórico dos objetos para decidir onde executar os Pods
Por quê: O etcd é o armazenamento do estado do cluster. O API Server é o único componente que conversa diretamente com ele; kubelet executa containers no nó, kube-proxy cuida das regras de rede dos Services e o Scheduler apenas escolhe o nó de cada Pod.
Questão 10 · Balanceamento de carga
Um portal precisa enviar as requisições com caminho /api/* para um grupo de instâncias da API e as demais requisições para outro grupo, que serve o site, usando um único endereço público HTTPS.
Qual recurso do Application Load Balancer atende a essa necessidade?
● Regras do listener com condição de caminho, encaminhando cada padrão para um target group diferente
○ Um Network Load Balancer, que inspeciona o caminho HTTP na camada 4
○ Um único target group com as duas aplicações, já que o ALB não diferencia caminhos
○ O NAT Gateway, que encaminha requisições por caminho para as subnets privadas
Por quê: O ALB atua na camada 7 e suas regras podem encaminhar por caminho, host, cabeçalhos ou parâmetros para target groups distintos. O NLB opera na camada 4 (TCP/UDP/TLS) e não roteia por caminho HTTP.
Questão 11 · Observabilidade
O único alarme de uma API é disparado quando a CPU passa de 80%. Durante uma falha de dependência externa, a API respondeu erro 503 para metade das requisições por uma hora, com CPU em 15%, e nenhum alerta foi emitido.
Qual melhoria no monitoramento é mais adequada?
● Criar alertas orientados pelos quatro sinais de ouro, incluindo taxa de erros e latência, com limites e janelas definidos
○ Reduzir o limite do alarme de CPU para 10%, para que ele dispare em qualquer problema
○ Substituir o alarme de CPU por uma trilha do CloudTrail, que mede a taxa de erros da API
○ Remover os alarmes e analisar apenas os logs quando um usuário reclamar
Por quê: CPU sozinha não é evidência suficiente de saúde. Latência, tráfego, erros e saturação dão uma visão do serviço como o usuário o percebe. O CloudTrail é auditoria de ações, não mede erros da aplicação.
Questão 12 · Segurança — IAM
Uma aplicação precisa apenas ler um único segredo do Secrets Manager com a senha do seu banco. A role associada a ela tem uma política que permite todas as ações do Secrets Manager em todos os segredos da conta.
Qual ajuste aplica o princípio do menor privilégio?
● Restringir a política à ação de leitura do valor do segredo (GetSecretValue) e apenas ao segredo do banco
○ Manter a política, pois a role já é uma credencial temporária e não precisa de restrições
○ Trocar a role pela access key do usuário root, que tem controle mais simples
○ Remover a política e gravar a senha em uma variável no código, eliminando a necessidade de permissões
Por quê: Menor privilégio significa conceder somente as ações e os recursos necessários. Credenciais temporárias reduzem a exposição, mas não limitam o que a identidade pode fazer; isso é papel da política.
Questão 13 · EC2 e armazenamento
Um analista guardou arquivos temporários de processamento no disco local (instance store) de uma instância EC2. Depois de parar e iniciar a instância para trocar o tipo, os arquivos não estavam mais lá. Os dados gravados no volume EBS raiz continuavam intactos.
Qual explicação é correta?
● O instance store é armazenamento temporário do host e perde os dados quando a instância é parada ou encerrada; o EBS é persistente e independente da vida da instância
○ O EBS e o instance store são equivalentes; a perda foi causada pela AMI usada na criação
○ O instance store é replicado em todas as AZs, por isso os dados foram movidos para outra zona
○ Os dados foram apagados porque o volume EBS faz balanceamento de carga entre discos
Por quê: O instance store fica no host físico e é temporário. O EBS é armazenamento de bloco persistente, em uma AZ, com suporte a snapshots. Dados que precisam sobreviver não devem ficar no instance store.
Questão 14 · Observabilidade
Uma equipe suspeita que a aplicação em uma instância EC2 está consumindo memória demais, mas no CloudWatch só encontra métricas como CPU, rede e disco do hipervisor. Não há métrica de uso de memória.
O que explica isso e como resolver?
● O uso de memória é medido dentro do sistema operacional e não é coletado por padrão; é preciso instalar e configurar o CloudWatch agent
○ O CloudWatch não suporta métricas de memória em nenhuma situação
○ A métrica de memória só aparece no CloudTrail, que audita o sistema operacional
○ Basta habilitar o monitoramento detalhado de 1 minuto, que inclui automaticamente a memória
Por quê: As métricas padrão do EC2 vêm do hipervisor. Memória e uso de disco do sistema de arquivos exigem um agente dentro da instância (CloudWatch agent; no Google Cloud, o Ops Agent). O monitoramento detalhado só aumenta a frequência das métricas padrão.
Questão 15 · Armazenamento de objetos
Um script com erro sobrescreveu vários contratos armazenados em um bucket com novas versões vazias. A empresa quer, daqui em diante, conseguir recuperar o conteúdo anterior de um objeto sobrescrito ou excluído por engano.
Qual recurso do armazenamento de objetos atende a esse objetivo?
● O versionamento do bucket, que mantém as versões anteriores dos objetos
○ Uma regra de ciclo de vida que move os contratos para uma classe fria
○ Uma presigned URL para cada contrato, gerada antes da sobrescrita
○ Um Security Group no bucket bloqueando gravações
Por quê: Com o versionamento, sobrescritas e exclusões geram novas versões ou marcadores, e as versões anteriores podem ser recuperadas. Ciclo de vida trata de custo e retenção, URLs assinadas tratam de acesso temporário, e buckets não usam Security Groups.
Questão 16 · Armazenamento de objetos
Para economizar, uma escola configurou uma regra de ciclo de vida que move os vídeos de aula para o S3 Glacier Deep Archive um dia após o envio. Os alunos assistem a esses vídeos toda semana, e agora as solicitações demoram horas e a conta de recuperação aumentou.
Qual análise é correta?
● A classe escolhida é para retenção de longo prazo, com recuperação demorada e cobrada; a regra deve considerar o padrão de acesso e usar uma classe compatível
○ Classes frias sempre têm o mesmo tempo de acesso da classe Standard; o problema está na rede dos alunos
○ Regras de ciclo de vida só podem excluir objetos, por isso a transição não foi aplicada
○ O bucket precisa ser público para que objetos em classes frias sejam lidos imediatamente
Por quê: Classes frias reduzem o custo de armazenamento, mas têm taxa de recuperação, duração mínima cobrada e, no Deep Archive, recuperação em horas. Regras de ciclo de vida fazem transição e expiração e devem ser compatíveis com o acesso esperado.
Questão 17 · Banco relacional — réplicas
Um painel de vendas lê de uma réplica de leitura do RDS. Logo após um cliente finalizar uma compra, gravada na instância principal, o painel ainda não mostra o pedido; alguns segundos depois, ele aparece.
Qual explicação é correta?
● A réplica de leitura recebe as alterações por replicação assíncrona, que pode ter defasagem em relação ao principal
○ A réplica é atualizada apenas uma vez por dia, a partir do backup automático
○ A gravação falhou na instância principal e foi refeita automaticamente pela réplica
○ A réplica de leitura é o standby da Multi-AZ e só recebe dados após um failover
Por quê: Réplicas de leitura usam replicação assíncrona e podem apresentar replica lag. Elas servem para consultas que toleram pequena defasagem; leituras que precisam do dado mais recente devem ir à instância principal.
Questão 18 · Kubernetes — probes
Um serviço de relatórios, de vez em quando, entra em travamento interno: o processo continua existindo, mas para de responder a qualquer requisição até ser reiniciado manualmente.
Qual verificação de saúde permite ao Kubernetes recuperar esse container automaticamente?
● Uma liveness probe, cuja falha repetida faz o kubelet reiniciar o container
○ Uma readiness probe, cuja falha faz o kubelet recriar a imagem do container
○ Uma startup probe, que continua verificando o container durante toda a sua execução e substitui a liveness
○ Um Service do tipo LoadBalancer, que reinicia automaticamente containers travados
Por quê: A liveness probe detecta containers que não estão mais funcionando e, ao falhar além do limite configurado, o kubelet reinicia o container. A readiness apenas controla o tráfego, e a startup atua somente durante a inicialização.
Questão 19 · Kubernetes — atualização e rollback
Em um pipeline de entrega, após executar kubectl set image no Deployment api, o próximo passo deve aguardar e acompanhar a atualização até que ela seja concluída ou fique travada.
Qual comando cumpre esse papel?
● kubectl rollout status deployment/api
○ kubectl rollout history deployment/api
○ kubectl rollout undo deployment/api
○ kubectl get namespaces
Por quê: rollout status acompanha o andamento da atualização. rollout history apenas lista as revisões, rollout undo retorna a uma revisão anterior e get namespaces não tem relação com a atualização.
Questão 20 · Kubernetes — configuração e segurança
Um desenvolvedor argumenta que guardar a chave de uma API de pagamentos em um Secret já é suficiente, porque no manifesto o valor aparece como um texto ilegível.
Qual análise está correta?
● O valor está apenas codificado em Base64; é preciso restringir a leitura com RBAC e verificar se a criptografia em repouso do etcd está habilitada
○ O Base64 do Secret é uma criptografia forte, que dispensa qualquer controle de acesso
○ Secrets são sempre cifrados no etcd por padrão em qualquer cluster, portanto nenhuma configuração é necessária
○ A chave deveria ficar em um ConfigMap, que cifra automaticamente os valores sensíveis
Por quê: Base64 é codificação reversível, não criptografia. Por padrão o Kubernetes guarda Secrets sem criptografia no etcd; a proteção depende de habilitar a criptografia em repouso e de limitar com RBAC quem pode ler Secrets. ConfigMap é para dados não sensíveis.
Questão 21 · Redes — VPC
Instâncias de uma subnet privada precisam baixar atualizações de pacotes da internet, mas não podem aceitar conexões iniciadas a partir da internet.
Qual configuração atende a esse requisito?
● Um NAT Gateway em uma subnet pública e, na tabela de rotas da subnet privada, a rota 0.0.0.0/0 apontando para ele
○ Uma rota 0.0.0.0/0 da subnet privada diretamente para o Internet Gateway, com IP público em cada instância
○ Um Security Group associado ao NAT Gateway liberando todas as portas de entrada
○ Uma réplica de leitura do banco na subnet pública, usada como saída para a internet
Por quê: O NAT Gateway permite conexões de saída iniciadas pelas instâncias privadas e não aceita conexões iniciadas de fora. Rota direta para o Internet Gateway tornaria a subnet pública. Não é possível associar Security Group a um NAT Gateway.
Questão 22 · Serverless — Cloud Run
Um serviço interno no Google Cloud Run recebe poucas requisições por dia. Os usuários percebem que a primeira requisição após um longo período sem uso demora mais do que as seguintes.
Qual explicação e qual ajuste são coerentes?
● Sem tráfego, o serviço pode ser reduzido a zero instâncias e a primeira requisição precisa iniciar uma; configurar um mínimo de instâncias reduz essa espera, com custo adicional
○ O Cloud Run apaga a imagem do container quando não há tráfego, e é preciso republicá-la a cada uso
○ Essa demora ocorre em qualquer serviço serverless, inclusive em tarefas Fargate mantidas por um service
○ A lentidão indica falta de permissões da service account, que só são carregadas na primeira requisição
Por quê: A escala a zero, comum no modelo sob demanda, gera inicialização a frio (cold start) quando chega a primeira requisição. Manter instâncias mínimas evita a espera, mas gera cobrança mesmo sem tráfego. Uma tarefa Fargate mantida por um service não escala a zero sozinha.
Questão 23 · Banco relacional — disponibilidade
A instância primária de um RDS configurado como Multi-AZ DB instance ficou indisponível por falha na sua zona de disponibilidade. A aplicação se conecta ao endpoint do banco fornecido pelo RDS.
O que ocorre nesse cenário?
● O RDS promove o standby da outra AZ e mantém o mesmo endpoint DNS; a aplicação precisa apenas reconectar
○ A aplicação passa a ler e gravar na réplica de leitura, que assume automaticamente como primária
○ Os dados são restaurados do último backup automático para uma nova instância, com perda das últimas horas
○ O standby já atendia metade das consultas e passa a atender todas, sem interrupção nenhuma
Por quê: Na Multi-AZ DB instance, o standby recebe replicação síncrona, não atende consultas e existe para o failover automático. O endpoint DNS é mantido, e a aplicação só precisa restabelecer as conexões.
Questão 24 · Alta disponibilidade
Usuários de uma loja virtual são desconectados de repente sempre que o Auto Scaling remove instâncias no fim do pico. A aplicação guarda a sessão do usuário na memória da instância que o atendeu.
Qual mudança de arquitetura resolve o problema de forma adequada?
● Tornar as instâncias sem estado, guardando sessões em um armazenamento externo compartilhado
○ Desativar a redução de capacidade, mantendo sempre o número máximo de instâncias
○ Guardar as sessões no instance store, que é preservado quando a instância é encerrada
○ Gravar as sessões na AMI, para que toda instância nova já tenha as sessões dos usuários
Por quê: Para que o Auto Scaling possa criar e remover instâncias livremente, elas devem ser sem estado: sessões, arquivos e dados ficam fora delas. Manter o máximo sempre elimina a economia da escala, e instance store e AMI não servem para isso.
Questão 25 · Auditoria
Na manhã de segunda-feira, a equipe descobre que uma regra que liberava a porta 22 para qualquer endereço foi adicionada a um Security Group durante o fim de semana. É preciso descobrir qual identidade fez a alteração e quando.
Qual fonte de informação é a adequada para essa investigação?
● O AWS CloudTrail, que registra as chamadas de API com identidade, horário e origem
○ As métricas de CPU do CloudWatch das instâncias afetadas
○ Os traces distribuídos da aplicação, que mostram as alterações de rede
○ O reader endpoint do banco de dados, que guarda o histórico da conta
Por quê: Alterações de configuração feitas por API, console ou CLI são registradas pelo CloudTrail como eventos de gerenciamento, com quem executou, quando e de onde. Métricas e traces são sinais operacionais e não identificam quem alterou uma configuração.
Questão 26 · Kubernetes — Services
Um serviço de pagamentos foi configurado com o IP de um Pod da API de estoque escrito diretamente no código. Após uma atualização do Deployment do estoque, os pagamentos passaram a falhar com erro de conexão, embora os novos Pods do estoque estejam Running e Ready.
Qual é a causa e a correção adequada?
● Os Pods substitutos recebem novos IPs; o serviço deve acessar o estoque por um Service, que oferece nome DNS e IP estáveis
○ O Deployment preserva os IPs dos Pods, então o problema está no kubelet e basta reiniciar o nó
○ Pods Ready não aceitam conexões de outros Pods; é preciso deixá-los em Pending
○ O IP do Pod deve ser gravado em um ConfigMap, o que impede que ele mude durante a atualização
Por quê: Pods são efêmeros: cada Pod criado por um rolling update é um objeto novo, com outro nome e, em geral, outro IP. O Service seleciona os Pods por labels e mantém um ponto de acesso estável, independentemente das substituições.
Questão 27 · Serverless
Uma rotina noturna de conciliação financeira leva cerca de 50 minutos para processar todos os registros em uma única execução. A equipe pensa em migrá-la para uma função AWS Lambda sem alterar sua lógica.
Qual análise é adequada?
● Uma invocação do Lambda tem duração máxima de 15 minutos; a rotina precisa ser dividida em partes menores ou executada como tarefa em container, por exemplo no ECS com Fargate
○ O Lambda não tem limite de duração, pois é serverless e escala sem restrições
○ Basta aumentar a memória da função para 10 GB, o que elimina o limite de tempo
○ Toda solução serverless tem o mesmo limite de 15 minutos, portanto a rotina só pode rodar em EC2
Por quê: O limite de 15 minutos é do Lambda, não de todo serverless. Uma tarefa no Fargate pode rodar continuamente. Aumentar a memória aumenta CPU disponível, mas não muda o tempo máximo da invocação.
Questão 28 · Segurança
Um estagiário publicou por engano, em um repositório público, um arquivo com a access key de um usuário IAM. Dez minutos depois, fez um novo commit removendo o arquivo.
Qual deve ser a primeira ação?
● Desativar ou revogar e rotacionar imediatamente a chave exposta, e depois investigar seu uso na auditoria
○ Nenhuma, porque o novo commit removeu o arquivo e a chave deixou de ser acessível
○ Codificar a chave em Base64 e publicá-la novamente para ocultar o valor original
○ Gravar a mesma chave em uma AMI privada, que passa a protegê-la
Por quê: A chave continua no histórico do repositório e pode já ter sido copiada. A credencial exposta deve ser revogada ou rotacionada imediatamente; em seguida, investiga-se seu uso no CloudTrail e substitui-se o uso de chaves fixas por roles e por um gerenciador de segredos.
Questão 29 · Kubernetes — Services
Um Service com selector app: catalogo tem port 80 e targetPort 80. Os Pods do catálogo estão Running e Ready, aparecem nos endpoints do Service, mas o container da aplicação escuta na porta 8080. As requisições ao Service retornam conexão recusada.
Qual ajuste resolve o problema?
● Alterar o targetPort do Service para 8080, a porta em que o container realmente escuta
○ Alterar o selector para app: frontend, pois os endpoints estão corretos
○ Aumentar o número de réplicas do Deployment para que alguma delas aceite a porta 80
○ Trocar o Service por um PersistentVolumeClaim para encaminhar as conexões
Por quê: port é a porta em que o Service escuta; targetPort é a porta do container para onde o tráfego é enviado. Como os endpoints existem, o selector está correto; o problema é o targetPort apontando para uma porta sem processo escutando.
Questão 30 · Kubernetes — diagnóstico
Depois de uma atualização, os novos Pods ficam no estado ImagePullBackOff. O kubectl describe pod mostra, nos eventos, falhas ao obter a imagem informada no Deployment.
Qual é a causa mais provável?
● O nome ou a tag da imagem estão errados, ou falta permissão para acessar o registry
○ Falta de CPU nos nós, pois esse estado indica que o Scheduler não encontrou espaço
○ A readiness probe falhou, o que impede o download da imagem
○ O selector do Service não corresponde às labels dos Pods
Por quê: ImagePullBackOff/ErrImagePull indicam que o kubelet não conseguiu baixar a imagem: nome ou tag inexistentes, ou credenciais do registry ausentes. Falta de recursos deixaria o Pod Pending (FailedScheduling), e probes ou selectors não afetam o download.
Questão 31 · Banco relacional — Aurora
Uma aplicação foi configurada para gravar no instance endpoint da instância que, na época da implantação, era a escritora de um cluster Aurora. Após um failover, essa instância virou réplica e as gravações começaram a falhar.
Qual configuração evita esse problema?
● Gravar pelo cluster endpoint, que aponta sempre para a instância escritora atual
○ Gravar pelo reader endpoint, que distribui as gravações entre as réplicas
○ Fixar o instance endpoint de outra réplica, que nunca participa de failover
○ Desativar o failover do cluster para que a escritora nunca mude
Por quê: O cluster endpoint (writer endpoint) acompanha a instância primária, inclusive após failover. O reader endpoint distribui conexões de leitura entre as réplicas, e instance endpoints apontam para uma instância específica, sem considerar sua função.
Questão 32 · Segurança — criptografia
Uma aplicação usa o AWS KMS com criptografia envelopada para proteger arquivos grandes. Um colega pergunta qual chave cifra o conteúdo dos arquivos e qual papel a chave do KMS desempenha.
Qual descrição está correta?
● Uma chave de dados cifra os arquivos, e a chave do KMS cifra essa chave de dados, que é guardada junto com os dados
○ A chave do KMS cifra diretamente cada arquivo, e a chave de dados é usada apenas para autenticação
○ A chave de dados e a chave do KMS são a mesma chave, apenas armazenadas em lugares diferentes
○ A criptografia envelopada dispensa políticas de acesso, porque ninguém consegue decifrar os dados
Por quê: Na criptografia envelopada, a chave de dados cifra os dados, e outra chave (a do KMS) protege a chave de dados. Quem tem permissão de usar a chave do KMS consegue decifrar, por isso a criptografia não substitui autorização nem auditoria.
Questão 33 · Serverless — ECS e Fargate
Uma nova tarefa no ECS com Fargate não chega a iniciar: o evento informa acesso negado ao baixar a imagem do Amazon ECR e ao criar o fluxo de logs no CloudWatch. A aplicação em si ainda não executou nenhuma linha de código.
Qual configuração deve ser revisada?
● A task execution role, usada pelo ECS/Fargate para baixar a imagem e enviar logs em nome da tarefa
○ A task role, que é usada exclusivamente para definir quantas tarefas o service mantém
○ O número desejado de tarefas do service, que controla as permissões de acesso ao ECR
○ A Security Group do banco de dados, que autoriza o download de imagens
Por quê: A task execution role dá ao ECS/Fargate permissão para baixar a imagem do ECR, enviar logs e obter segredos referenciados na task definition. A task role é usada pela aplicação dentro do container para chamar serviços AWS; nenhuma das duas define a quantidade de tarefas.
Questão 34 · Kubernetes — Services
Em um laboratório com Minikube, um aluno criou um Deployment de um site e precisa abri-lo no navegador da sua própria máquina, fora da rede interna do cluster. Não há balanceador de nuvem disponível.
Qual tipo de Service é adequado para esse acesso no laboratório?
● NodePort, que abre uma porta nos nós e permite o acesso externo, por exemplo com minikube service
○ ClusterIP, que já publica o Service automaticamente na internet
○ ExternalName, que cria réplicas do site e as expõe fora do cluster
○ Um Namespace, que funciona como endereço público para os Pods
Por quê: ClusterIP é acessível apenas dentro do cluster. NodePort abre uma porta (faixa padrão 30000–32767) em todos os nós e é o caminho usual em laboratórios locais. ExternalName apenas retorna um nome DNS externo, e Namespace é uma divisão lógica, não um endereço.
Questão 35 · Kubernetes — escalabilidade
Uma equipe criou um HorizontalPodAutoscaler baseado em uso de CPU para uma API, mas ele não consegue calcular a utilização e nunca altera o número de réplicas. Os containers da API foram declarados sem requests de recursos.
O que é necessário para o HPA funcionar com base em CPU?
● Ter um provedor de métricas, como o metrics-server, e definir requests de CPU nos containers
○ Instalar o Cluster Autoscaler, que substitui o HPA no cálculo de uso de CPU dos Pods
○ Remover a readiness probe, pois ela impede o HPA de ler métricas
○ Usar um Service ExternalName, que publica as métricas dos Pods para o HPA
Por quê: O HPA calcula a utilização de CPU em relação aos requests dos containers, lendo as métricas de recursos fornecidas pelo metrics-server. O Cluster Autoscaler é outro mecanismo: ele ajusta a quantidade de nós, não de réplicas.
